# AI-Agent-Bench: Security Threat Model

**Version:** 1.0-draft
**Status:** Documented security limitations and execution safeguards
**Security classification:** Local execution with explicit risk consent - not sandboxed

## 1. Purpose

This document describes the security boundaries, execution safeguards, threat assumptions, and known limitations of AI-Agent-Bench.

The benchmark executes code generated by LLM-powered agents. Such code must be treated as untrusted.

The current implementation includes several safeguards to constrain normal tool-mediated execution and reduce accidental exposure of sensitive environment variables.

However, it does not provide OS-level isolation.

**AI-Agent-Bench must not be described as a secure sandbox or as safe for executing malicious code.**

## 2. Security Objectives

The current security design aims to:

- Prevent real-model execution from occurring accidentally.
- Require explicit user consent before enabling unsafe local execution.
- Restrict commands available through the normal command-runner interface.
- Avoid shell-based command execution.
- Apply execution timeouts.
- Limit captured command output.
- Filter subprocess environment variables.
- Keep hidden tests and reference implementations outside the normal agent workspace.
- Document residual risks clearly.

These objectives describe intended safeguards, not guarantees against a malicious process.

## 3. Threat Model

### 3.1 Assets

The local execution environment may contain:

- API keys and credentials.
- Environment variables.
- Source code and project files.
- Git credentials and repository configuration.
- User documents.
- Local application data.
- Hidden benchmark tests.
- Reference implementations.
- Evaluation artifacts.
- Operating system resources.

These assets must be considered potentially accessible to code executing under the same operating-system user.

### 3.2 Threat actors

The threat model considers:

1. Malicious or compromised model outputs.
2. Agent-generated code that performs unintended operations.
3. Malicious task instructions or benchmark content.
4. Accidental execution of destructive commands.
5. Attempts to inspect or manipulate evaluation assets.
6. Attempts to access credentials or unrelated host files.

The model output is untrusted even when generated by a reputable provider.

### 3.3 Trust boundaries

The main logical components are:

- Benchmark orchestrator.
- Agent runtime.
- Tool registry.
- Command runner.
- Agent workspace.
- Test evaluator.
- Hidden test assets.
- Local operating system.

These components are not separated by a hardened operating-system security boundary.

## 4. Current Execution Safeguards

### 4.1 Explicit execution consent

Real-model execution is disabled by default.

The orchestrator requires the `allow_unsafe_local_execution` option to be enabled before proceeding.

The CLI exposes this option through:

`--allow-unsafe-local-execution`

When enabled, the CLI displays a warning that agent and evaluator code are not OS-isolated.

This is an explicit consent mechanism, not a security isolation mechanism.

### 4.2 Command allowlist

The command runner restricts executable names through an allowlist.

The current implementation includes:

- Python executable names.
- Pytest executable names.

This constrains commands invoked through the normal command-runner interface.

It does not prevent arbitrary Python code from accessing other system capabilities.

### 4.3 Shell execution

Subprocess execution uses:

`shell=False`

This avoids invoking commands through the operating-system shell by default.

However, a permitted interpreter can still execute arbitrary code through its arguments.

For example, Python command arguments can execute code that accesses files and processes available to the current user.

### 4.4 Workspace restrictions

Normal tool operations are scoped to a benchmark workspace.

The workspace builder copies permitted starter files and visible tests.

Hidden tests and reference implementation files are not intentionally copied into the agent workspace.

This is a logical separation of benchmark assets.

It is not a filesystem security boundary.

Agent-generated code can potentially access files outside the workspace through absolute paths or other filesystem operations.

### 4.5 Environment filtering

The command runner passes only explicitly permitted environment variables to subprocesses.

The current allowlist includes:

- PATH
- SYSTEMROOT
- SYSTEMDRIVE
- WINDIR
- TEMP
- TMP
- PATHEXT
- PYTHONPATH
- PYTEST_DISABLE_PLUGIN_AUTOLOAD

This reduces accidental inheritance of environment variables such as API keys.

It does not prevent code from reading accessible files, inspecting operating-system resources, or obtaining information through other permitted mechanisms.

### 4.6 Execution timeouts

Subprocess execution is subject to configured timeouts.

This helps prevent indefinitely running commands through the normal command-runner interface.

A timeout does not provide complete process containment or guarantee that all descendant processes are terminated.

### 4.7 Output limits

Command output is truncated according to configured limits.

This reduces excessive output capture.

It does not prevent a process from performing other operations before producing output.

## 5. Known Security Limitations

The current architecture has significant limitations.

### 5.1 No OS-level sandbox

Agent-generated code executes under the same operating-system user as the benchmark process.

It may access files, directories, processes, and resources permitted to that user.

### 5.2 Arbitrary Python execution

The executable allowlist permits Python execution.

Python can access the filesystem, environment, subprocess APIs, and other system capabilities available to the executing user.

An executable allowlist is therefore not equivalent to a restricted programming environment.

### 5.3 Credential exposure

Environment filtering reduces direct exposure of inherited environment variables.

However, credentials may also exist in:

- `.env` files.
- Configuration files.
- Application directories.
- Shell configuration.
- Other accessible local files.

The current architecture does not prevent agent-generated code from reading these files if filesystem permissions permit access.

### 5.4 Evaluator integrity

Hidden tests execute against an agent-modified workspace.

Agent-generated code may modify workspace files that are subsequently imported or executed during evaluation.

The current architecture does not guarantee evaluator integrity against a malicious agent.

### 5.5 Filesystem traversal

Workspace restrictions apply to normal tool operations.

They do not prevent arbitrary Python code from using absolute paths, symbolic links, or other filesystem mechanisms to access locations outside the workspace.

### 5.6 Process isolation

The current command runner does not establish a hardened process boundary.

Timeouts and subprocess execution controls should not be interpreted as comprehensive process isolation.

## 6. Security Risk Assessment

| Risk                                     | Current mitigation            | Residual risk                                    |
| ---------------------------------------- | ----------------------------- | ------------------------------------------------ |
| Accidental real-model execution          | Explicit opt-in               | User can authorize unsafe execution              |
| API key inheritance                      | Environment allowlist         | Credentials may exist in accessible files        |
| Arbitrary command invocation             | Executable allowlist          | Allowed Python can execute arbitrary code        |
| Shell injection through shell invocation | `shell=False`                 | Interpreter arguments remain powerful            |
| Workspace traversal                      | Normal tool path restrictions | Arbitrary code can access host paths             |
| Hidden-test exposure                     | Separate workspace copying    | No hardened filesystem isolation                 |
| Evaluator manipulation                   | Evaluation after agent stops  | Agent can modify evaluated workspace             |
| Long-running commands                    | Timeouts                      | Descendant-process containment is not guaranteed |
| Excessive command output                 | Output truncation             | Other side effects remain possible               |

## 7. Safe Operating Recommendations

Until stronger isolation is implemented:

1. Prefer mock-provider execution for development and testing.
2. Do not execute untrusted agent-generated code on a machine containing sensitive information.
3. Do not use the unsafe execution option casually.
4. Do not store valuable credentials in the same user environment used for benchmark execution.
5. Use a disposable environment for experiments involving untrusted models or task content.
6. Keep benchmark assets and repository credentials backed up.
7. Review generated code and command behavior before executing untrusted workloads.
8. Never describe the current implementation as a secure sandbox.

A disposable environment reduces potential impact only to the extent that its isolation is properly configured. A normal project workspace or Python virtual environment is not a security boundary.

## 8. Future Security Architecture

A future hardened execution environment should investigate:

### 8.1 OS-level isolation

Potential approaches include:

- Dedicated virtual machines.
- Container isolation with appropriate hardening.
- Restricted operating-system users.
- Filesystem access controls.
- Network isolation.
- Process and resource restrictions.

No particular mechanism should be considered secure without testing its configuration and threat assumptions.

### 8.2 Evaluator isolation

Future designs should consider:

- Separate evaluator processes.
- Immutable trusted test assets.
- Read-only reference assets.
- Isolated evaluation workspaces.
- Controlled result transfer.
- Protection against agent-modified imports and test files.

### 8.3 Credential isolation

Future execution infrastructure should ensure agent processes cannot access provider credentials or unrelated application secrets.

Credential access should be separated from the agent execution environment.

### 8.4 Network controls

Network access should be explicitly controlled according to the benchmark task requirements.

Tasks that do not require external network access should ideally execute without it.

### 8.5 Resource controls

Future execution environments should provide explicit limits for:

- CPU usage.
- Memory consumption.
- Disk usage.
- Process count.
- Execution duration.
- Network access.

## 9. Security Validation Requirements

Before claiming stronger execution security, the project should undergo tests covering:

- Filesystem access outside the workspace.
- Environment variable exposure.
- Credential access attempts.
- Process creation.
- Network access.
- Symlink and path traversal.
- Hidden-test access attempts.
- Evaluator tampering.
- Timeout and process termination behavior.
- Resource exhaustion.

A security claim must be supported by testing the actual deployed execution configuration.

## 10. Current Security Status

The current AI-Agent-Bench implementation provides limited local execution safeguards and explicit user consent for unsafe real-model execution.

It does not provide:

- OS-level sandboxing.
- Guaranteed filesystem isolation.
- Guaranteed credential isolation.
- Network isolation.
- Tamper-proof evaluator execution.
- Comprehensive process containment.

**Security conclusion:** AI-Agent-Bench is an unsandboxed local execution framework with limited execution safeguards. It is an engineering MVP, not a hardened environment for hostile code execution.
